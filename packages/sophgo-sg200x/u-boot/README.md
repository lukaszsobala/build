# Cvitek board files for the vendor U-Boot

The Sophgo SG200x vendor U-Boot (`sophgo/u-boot-2021.10`) does not build on its
own. The board description lives outside the U-Boot tree, in
`duo-buildroot-sdk-v2` under `build/boards/`, and the SDK's `build/Makefile`
copies or symlinks it in just before running `make`. Armbian does not carry the
1.3 GB SDK, so the handful of files it injects are vendored here instead.

`pre_config_uboot_target__sophgo_sg200x_board_files()` in
`config/sources/families/include/sophgo-sg200x_common.inc` copies them into the
U-Boot tree after patching and before `make <defconfig>`.

## Provenance

Everything here comes from `milkv-duo/duo-buildroot-sdk-v2` (branch `main`,
2026-07-28), for two boards: `sg2000_milkv_duos_glibc_arm64_sd` (`arm64/`) and
`sg2000_milkv_duos_musl_riscv64_sd` (`riscv64/`). `common/` is shared.

The two SDK board directories are near-identical: `memmap.py`,
`cvi_board_init.c` and `cvitek.h` are byte-for-byte the same, and
`partition_sd.xml` differs only in the ROOTFS size, which reaches U-Boot as
`ROOTFS_PART_SIZE` in `cvipart.h` and only matters to the vendor `sdboot`
fallback Armbian does not use. The real differences are the defconfig
(`CONFIG_RISCV=y` vs `CONFIG_ARM=y` and friends) and which base dtsi the board
DTS includes.

| Vendored path | SDK source | Destination in the U-Boot tree |
|---|---|---|
`<arch>` below is `arm64` or `riscv64`; the destination DTS directory is
`arch/arm/dts/` for ARM (U-Boot 2021.10 has no `arch/arm64`) and
`arch/riscv/dts/` for RISC-V. Both come from `SOPHGO_CVI_UBOOT_DTS_DIR`.

| Vendored path | SDK source | Destination in the U-Boot tree |
|---|---|---|
| `common/dts/*.dtsi` | `build/boards/default/dts/cv181x/` | `<dts dir>` |
| `arm64/dts/cv181x_base_arm.dtsi` | `build/boards/default/dts/cv181x_arm64/` | `arch/arm/dts/` |
| `riscv64/dts/cv181x_base_riscv.dtsi` | `build/boards/default/dts/cv181x_riscv/` | `arch/riscv/dts/` |
| `<arch>/dts/sg2000_milkv_duos_….dts` | `<board>/dts_arm64/` or `<board>/dts_riscv/` | `<dts dir>` |
| `<arch>/configs/cvitek_…_defconfig` | `<board>/u-boot/` | `configs/` |
| `<arch>/board/cvi_board_init.c` | `<board>/u-boot/` | `board/cvitek/cvi_board_init.c` |
| `<arch>/include/cvitek.h` | `<board>/u-boot/` | `include/cvitek/cvitek.h` |
| `<arch>/include/cvi_board_memmap.h` | generated from `<board>/memmap.py` | `include/` |
| `<arch>/include/cvipart.h` | generated by `mkcvipart.py` from `<board>/partition/partition_sd.xml` | `include/` |
| `<arch>/include/imgs.h` | generated by `mk_imgHeader.py` from the same XML | `include/` |

where `<board>` is `build/boards/cv181x/<the SDK project for that arch>`.

The last three are *generated* by the SDK rather than checked in there. They are
deterministic for a given board, so the generated output is vendored directly
and Armbian needs no Python tooling from the SDK.

## Local modifications

Both defconfigs have one line the SDK does not have:

```
CONFIG_OF_LIBFDT_OVERLAY=y
```

This is queenkjuul's `milkv-bootloader` patch 0004, needed for `fdtoverlays` in
`extlinux.conf`.

The RISC-V defconfig additionally turns off the cvitek video stack
(`CONFIG_DM_VIDEO`, `CONFIG_VIDEO_CVITEK`, `CONFIG_CMD_CVI_VO`). The reasoning
is in a comment block in the file itself: `cvi_mipi.c` does DSI lane timing in
floating point and needs soft-float helpers from an `lp64` libgcc, which the
vendor toolchain has and Debian's `riscv64-linux-gnu-gcc` does not. Nothing in
the Armbian boot path draws anything in U-Boot, so it costs nothing.

Everything else is byte-identical to the SDK.

## Re-syncing after an SDK update

```bash
git clone --depth 1 https://github.com/milkv-duo/duo-buildroot-sdk-v2
cd duo-buildroot-sdk-v2
source build/envsetup_soc.sh
defconfig sg2000_milkv_duos_glibc_arm64_sd   # or …_musl_riscv64_sd
make -C build u-boot-build          # generates the three headers, then fails at
                                    # compile if you have no cross toolchain
```

The generated headers land in `build/output/<board>/cvi_board_memmap.h` and
`u-boot-2021.10/include/{cvipart.h,imgs.h}`. The three generators can also be run
directly, which is quicker and needs no toolchain:

```bash
python3 build/scripts/mmap_conv.py --type h \
    build/boards/cv181x/<board>/memmap.py cvi_board_memmap.h
python3 build/tools/common/image_tool/mkcvipart.py \
    build/boards/cv181x/<board>/partition/partition_sd.xml .
python3 build/tools/common/image_tool/mk_imgHeader.py \
    build/boards/cv181x/<board>/partition/partition_sd.xml .
```

Note `cvi_board_memmap.h`'s include guard carries a hash of the project name, so
the ARM and RISC-V copies differ in those two lines and nowhere else.

Re-apply the local modifications listed above afterwards.

## Editing these files does not invalidate the artifact cache

The u-boot artifact version is computed from the patch directories, the family
hook and function bodies, and a fixed list of variables — see
`artifact_uboot_prepare_version()` in
`lib/functions/artifacts/artifact-uboot.sh`. This directory is not in any of
them, so changing a defconfig or a dts here leaves the hash identical and
Armbian happily reuses the previously built `.deb`.

`ARTIFACT_IGNORE_CACHE=yes` alone is not enough. It does force a fresh build,
but the previously built `.deb` is still sitting in `output/packages-hashed/`
under the unchanged version string, and the next *image* build restores it right
back over `output/debs/` — so the image silently ships the old bootloader even
though you just watched a new one being built. Delete both copies first:

```bash
rm -f output/packages-hashed/global/linux-u-boot-milkv-duos-riscv-edge_*.deb \
      output/debs/linux-u-boot-milkv-duos-riscv-edge_*.deb
./compile.sh uboot BOARD=milkv-duos-riscv BRANCH=edge ARTIFACT_IGNORE_CACHE=yes
```

Symptoms, in the order you are likely to meet them: a u-boot build that finishes
in a couple of seconds reporting the same version string as before, and then an
image whose `/boot/fip.bin` does not match the one in the `.deb` you just built.
Comparing the two is the quickest way to confirm:

```bash
mcopy -n -i "output/images/<image>.img@@1048576" ::/fip.bin /tmp/fip-from-image.bin
dpkg-deb -x output/debs/linux-u-boot-milkv-duos-riscv-edge_*.deb /tmp/ub
md5sum /tmp/fip-from-image.bin /tmp/ub/usr/lib/linux-u-boot-edge-milkv-duos-riscv/fip.bin
```

(1048576 is partition 1's start, 2048 sectors x 512.)

## Not here

Genuine modifications to vendor U-Boot *source* are real patches, in
`patch/u-boot/u-boot-sophgo-sg200x/`. This directory is only files the SDK
injects verbatim.

OpenSBI is not here either. RISC-V needs it for the monitor slot of `fip.bin`,
and it is built from `sophgo/opensbi` (branch `sg200x-dev`) by
`sophgo_sg200x_build_opensbi()` in the family include.
